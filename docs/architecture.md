# Architecture

Context Drop has one main conversation and exactly four pool workers. Workspace tasks use a pool worker to coordinate a new or existing coding agent in a user workspace. Every worker runs the same configured agent: `pi`, `codex`, or `claude`.

The Go daemon owns iMessage, schedule timing, direct script execution, delivery receipts, and runtime supervision. Command schedules bypass the agent pool. The main Pi conversation can text the user through its final response and call `delegate_to_worker`, `list_workspaces`, or `delegate_to_workspace`. Discovery exposes bounded pane metadata, not terminal contents. No shell, raw pane control, thread management, or automatic authorization tools are exposed to it. Report turns cannot delegate work.

The Node runtime owns a durable FIFO task queue and four fixed slots. Each slot is an interactive agent TUI in a tab of the managed Herdr workspace, launched through the configured agent command (for example `dari --claude --dangerously-skip-permissions`). Workers start without a model request. The runtime drives them entirely through Herdr's agent API: each task writes a briefing file containing the parent instructions, the worker role, and the effective main conversation with its saved compaction summary rendered as a transcript, then submits the prompt with `herdr agent prompt`. A new task first resets the TUI (`/clear` for Claude, `/new` for Codex and Pi); follow-up turns continue in place. There is no extra summarization call or process startup per task.

Messages and schedule occurrences enter the same queue. Explicit worker selection is respected; schedules use the first available slot. A waiting worker retains its task and session. Delegating the user's answer to that worker resumes the same fork. A busy worker queues new tasks rather than silently treating unrelated messages as follow-ups.

Workers deliver answers with `context-drop report --final`, which completes the task immediately. Herdr's agent status is the fallback: a turn that ends idle without a final report completes with a placeholder, and a pane that becomes `blocked` fails the turn with its recent screen so the main can intervene. Explicit `context-drop report` calls send progress; `--question` asks for user input and leaves the worker waiting when its turn ends. All reports reach the main conversation with worker and task attribution. Workers do not have delegation or messaging tools.

Queue state and task-scoped report capabilities are persisted before native dispatch. Each schedule occurrence and main tool call has an idempotency key. Resumed turns have fresh identities within the same task capability. The per-slot assignment record and Herdr's state sequence allow completion recovery after runtime outages. Report delivery uses leases and receipts; ambiguous external sends are not retried automatically.

Native workers survive runtime restarts. Changing the worker agent (`context-drop config worker-agent`) takes effect on the next daemon restart: panes launched for a different agent are closed and relaunched, and any task running on them fails without replay. Running work is otherwise not resubmitted. A dispatch whose outcome is unknown retains its slot instead of risking duplicate execution. Pool status is available through `context-drop daemon status`.

The optional TTL upload server is independent: authenticated uploads and expiring bearer download links. It owns no agent or schedule state.

Incoming texts are grouped after a two-second quiet period (six-second maximum), retaining each original message as a durable job. One combined turn can finish silently. Delegation to an occupied worker adds context to the same task; each finished turn publishes its answer immediately as a `turn_completed` report, then pending additions run in the same session. Only the final `completed` report retires the task. Explicit `newTask` queues unrelated work separately. Parent instructions, including loaded AGENTS.md files, accompany each fork and are combined with the worker role. Worker questions and results are relayed naturally, without worker-number wrappers.

Agent commands are interactive launch argv, detected on daemon start and routed through `dari` when it is installed: `dari --codex --yolo`, `dari --claude --dangerously-skip-permissions`, `dari --pi --approve`. Each worker runs unattended inside its own tab, so the bypass-approvals flag is part of the command. The report CLI finds its task credentials through `HERDR_PANE_ID` in `managed/report-credentials.json`, which the runtime rewrites on every dispatch.

## Existing Herdr workspaces

Requests such as “start a new task in dari-mono” can target an existing workspace. The main discovers workspace and pane IDs, then uses `delegate_to_workspace(worker, workspace, mode, prompt, paneId?, cwd?, newTask?)`. `mode: new` instructs the coordinator to create an isolated gwt worktree and a new, named tab. `mode: continue` requires an exact existing agent pane and preserves its conversation and worktree—no reset, restart, move, or close. Multiple matching workspaces/conversations require clarification; new tasks in multi-directory workspaces require a discovered cwd. Missing targets never silently fall back.

A pool worker still coordinates, monitors, and reports this work; this is not direct runtime-controlled dispatch into user-owned panes. The runtime persists the destination and validates discovery, while the coordinator performs the Herdr actions. Later messages to that worker retain the destination and reuse the same task tab. A changed destination requires a separate task. Report turns cannot initiate either kind of delegation. Schedules and unspecified work retain the default four-slot pool.
